## Ground rules
- `src/sim/` stays pure TypeScript with no Three.js, DOM or network imports, so `npm run experiment` keeps running in Node.
- Renderers and integrations only read world state and never call `world.rng` or `world.agentRng`. Cosmetic randomness like tree placement comes from a hash of the tile index. The only writes are judge actions, which all go through one function that also records them with their tick for replays.
- Every new sim behaviour is a config option, and anything random gets its own RNG stream. With all of them switched off (e.g. a `--legacy` flag on the experiment script), `npm run experiment` must reproduce the committed `results/summary.csv` exactly; diff it after step 3 to prove the sim didn't drift.
- Network calls never block a tick. They're async, rate-limited and fire-and-forget from the sim's point of view.

## 2. Isometric 3D renderer
Add `three` and `@types/three`. Build the renderer in `src/render/iso/`, split by concern (scene and camera, terrain, trees, fire and smoke, drones, overlays, picking) so a few of us can work on it in parallel. Keep `src/render/renderer.ts` and reuse it as a small 2D minimap in a corner, showing the truth or the selected drone's belief.

Go for a Smashy Road-like look: chunky voxel/low-poly, flat-shaded with no textures, bold saturated colours, crisp directional shadows, toy-like, all geometry built from primitives with no external assets. Use an orthographic isometric camera with drag to pan, wheel to zoom, Q/E to rotate 90° (hills hide things) and a reset button.
- Each tile is a box column at its sim height, with a coloured top cap over earthy sides, using InstancedMesh throughout. `terrain.height` runs about 0–24 with 1 tile = 1 unit, so apply one vertical scale (start around 0.4) to everything: terrain, drone altitude (terrain + `droneAltitude`), the base mast (+6), link endpoints and smoke. That way links visibly clear or clip hills exactly where the sim's line-of-sight test says.
- Grass is bright green, forest darker green with 1–3 low-poly conifers per tile, sand pale yellow, rock grey with a boulder, and water flat blue with a gentle shimmer (the sim already flattens water).
- Burning tiles get flickering emissive voxel flames sized by `env.severity` (1–3). Burning trees lose foliage and turn charcoal, and burnt tiles go dark with the odd ember. Extinguished tiles are `Burnt` with wetness 1 (wetness only decays on unburnt tiles), so show them wet and dark, distinct from burnt-out ground. Wetted unburnt tiles get a faint blue tint.
- `env.smoke` drives grey semi-transparent low-poly puffs over each tile, opacity by density, drifting with `env.wind` (angle is the direction it blows towards, speed 0–1).
- The village's nine tiles become small houses with pitched coloured roofs that char if they burn. The base is a helipad with a radio mast that goes dark when `world.baseOnline` is false.
- Drones are tiny quadcopters with spinning rotors, body colour by state (reuse the 2D state colours), an ID label and small water, battery and damage bars, flying at their sim altitude. When a drone's `waterDropped` goes up, blue voxels fall and steam puffs if the tile was burning. Dead drones fall and leave a smoking wreck.
- Blackout zones are translucent purple domes, and usable links are glowing lines between nodes at altitude.

The current loop runs 1–12 whole ticks per animation frame, which reads as jumpy and far too fast in 3D. Replace it with a ticks-per-second control that goes slow enough to watch (around 5–30) up to the current maximum, add single-step, and interpolate drone positions between ticks.

Port every existing control and panel: mode, seed, new run, play/pause, the judge tools (select, start fire, blackout, crash drone), wind sliders, comms range, cut base comms, clear blackouts, smoke-blocks-comms, the view toggles, the selected drone's map with staleness fog, teammate guess clouds, sensor ring, selected-drone panel, stats and chart. Picking raycasts the pointer to a tile (instanceId → tile index) and then reuses the existing tool logic. Add a wind compass, a banner when the village is lost (the sim keeps running after that; don't change `World.finished`, the experiments rely on it), an end card when the run finishes (burnt area, village status, drones lost, water dropped, time to extinguish, plus replay and new-seed buttons), and a tile inspector for clicks that don't land near a drone.

Diff the fire and wetness arrays each tick and only update instances that changed. Hold 60 fps on a laptop with 10 drones on the 64×64 map.

## 3. Spec gaps in the sim
Each of these is a config option. Choose the defaults the 3D app should use, and give each one a visual.
- Smoke should need several burning tiles. On the current model, one isolated burning forest tile in calm wind peaks at about 1.7 smoke (grass about 1.2), above `thickSmoke` (0.8) and the comms-block level (1.2), while wind of 0.3 or more keeps it under 0.6. Make thick smoke impossible from a single tile at any wind speed.
- Smoke blocks comms by default, since the spec treats smoke between drones as infinite distance. Keep the toggle.
- Descending drains battery too, not just climbing.
- Add a drone-count slider (applied on New run) and an option to spawn the drones in a line on the pad.
- Add a pure function to comms.ts that says why a pair within range can't link (hill, smoke or blackout) without changing `canLink`. Draw those pairs as dashed links coloured by reason, so judges can watch links snap as drones go behind hills or into smoke.

## 4. Sponsor and MLH integrations
Everything here lives outside `src/sim/`. Add a small Node + TypeScript server in `server/` (HTTP API plus WebSocket, proxied by Vite in dev; in production it serves the built app) and a client layer in `src/integrations/`. The client layer derives one typed event stream by diffing world state each tick: fire spotted by the base, drone state changes, crashes, links lost and regained, base offline, village threatened or lost, fire out, and judge actions. The radio log, voices, AI commander, databases and ledger all consume that stream. Secrets live in a gitignored `.env` with a committed `.env.example`; only the server reads them, and nothing secret goes in the browser bundle. Each integration switches itself off when its key is missing and shows a status dot in the UI, so the demo still works offline on bad hackathon Wi-Fi.
- Tiger Data (Tiger Cloud: Postgres + TimescaleDB) is our live database. Create hypertables for drone telemetry (position, altitude, state, battery, damage, water), fire metrics (burning, burnt, thick-smoke tiles, comms groups, links, base online) and events, with `time` set to run start + tick seconds so `time_bucket` works for live and experiment runs alike. The browser batches telemetry to the server about once a second. Add continuous aggregates and a columnstore/compression policy, and build a `dashboard.html` page that reads from the aggregates: the live run (fire growth, connectivity, battery spread) and the experiment comparison (swarm vs central vs greedy across comms range). `npm run experiment -- --db` streams runs into the same database (downsampled, e.g. every 10 ticks, to stay inside the free tier), so the dashboard fills in while a sweep runs.
- Gemini (`@google/genai`, current Flash model, e.g. `gemini-3.8-flash`) is an AI incident commander at the base, and it only sees what the base knows: the zones `computeZones` finds on the base's belief map, which drones are in the base's comms group right now, and the last status heard from the rest. Every 20–30 seconds of wall-clock time, or on a major event, it writes a short radio-style sitrep for the radio log, labelled with how stale its information is. It takes typed or spoken judge commands through function calling, mapped onto the existing judge tools (start a fire, place a blackout, crash a drone, set wind, cut base comms), and shows a confirm chip before running any action. At the end of a run it writes an after-action report from the event log and the metrics in Tiger Data. It advises humans and drives judge tools only, never the drones, so the decentralised claim stays honest. When base comms are cut its sitreps visibly go stale, which is part of the pitch.
- ElevenLabs (`@elevenlabs/elevenlabs-js`) gives the sim its sound. Gemini's sitreps and key alerts are read out in a dispatcher voice. Drone radio calls (low battery, returning to base, refilling, lost link, crashed) use a few distinct voices, are pre-generated per drone and event, cached, and played through a radio filter (band-pass and squelch). A script, `npm run audio:generate`, uses the Sound Effects and Music APIs to make rotor, fire, splash, steam, crash, wind and squelch sounds plus calm, tense, critical, victory and defeat music stems in `public/audio/`, committed so the demo needs no network; the music crossfades with the threat level. Optionally add push-to-talk judge commands using ElevenLabs speech-to-text feeding Gemini.
- DurHack's theme is Composition, so make the swarm audible too. In a Web Audio layer each drone is a voice pitched by its ID, and drones that can reach each other play on a shared beat. A group that gets cut off drifts out of time and detunes, then snaps back into sync when it reconnects, so you can hear the network split and heal. Fire intensity drives the percussion.
- MongoDB Atlas stores scenarios and replays as documents. Because the sim is deterministic, seed + config + the recorded judge actions replay a run exactly, so save scenarios with a shareable `?scenario=<id>` link. Add a "Challenge the swarm" board: when someone saves a scenario, the server runs it headless in every mode (the sim already runs in Node), stores the outcomes and Gemini's after-action report, and ranks the scenarios that hurt the swarm most.
- Vultr hosts the demo and runs the big experiments. Add a Dockerfile and docker-compose (server plus built app behind HTTPS, e.g. Caddy) and deploy notes for a Vultr Cloud Compute instance. Give the experiment runner a `--workers N` option (worker_threads), and document a large sweep (e.g. 300 seeds per condition) on a high-CPU Vultr instance streaming into Tiger Data.


## 5. CBBA and forecasting (stretch)
- Add a `cbba` mode alongside the existing `swarm` auction, which stays as it is. Each drone builds a bundle of up to about 3 zones (the zone for its current load, then the next ones after refills) using time-discounted marginal scores, and drones run CBBA consensus (Choi, Brunet & How, 2009) on zone slots (zoneId#k) over the live network. Reuse the particle-filter tracker for teammates out of contact, as swarm mode does.
- Optionally let drones forecast the fire by running the spread model forward from their own belief map, and bid on where the front will be.
